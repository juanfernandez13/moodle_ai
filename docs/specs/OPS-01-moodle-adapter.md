# OPS-01 — Cadastro e datas no Moodle

Escopo autorizado: funções de cadastro/envio e datas do BUILDER_PIPELINE_PLAN, verificadas com dados fictícios no laboratório localhost. Restrição explícita do usuário: nunca acessar, usar ou testar o Moodle do IFCE. Nesta versão, MOODLE_URL e o perfil de capacidades permitem somente http://localhost:3211, o laboratório local criado para a execução; nunca aceitar URL alvo enviada pelo cliente. Perfil só pode anunciar capacidades cobertas por evidência real. Sem configuração, interface explica como configurar e não simula envio.

Interface de integração da UI:

- GET `/api/moodle/status`: `{configured,validated,authenticated,name?,profile,issues?}`. Configuração ausente não é erro de autenticação.
- POST `/api/moodle/login` JSON `{username,password}`: `{ok,name}` ou `{ok:false,issues:[{code,message}]}`. POST `/api/moodle/logout` desconecta.
- GET `/api/moodle/courses`: `{ok:true,courses:[{id:number,title:string,shortName?:string}]}`. GET `/api/moodle/course?courseId=N`: `{ok:true,course:{id,title},targets:DateTarget[]}` com IDs `section:N` / `module:N`, tipos e índice de unidade 0-based. Seção geral é omitida e tipos não suportados são informados.
- POST `/api/moodle/students/preview` JSON `{rows:StudentRow[],options:StudentOptions,expectedHash:string}`: recomputar CSV/hash em servidor e verificar revisão antes de subir ao rascunho Moodle; retornar `{ok:true,previewId,hash,rows:[{username,name?,email?,status}],issues?}` sem criar alunos. A prévia fica na sessão e inclui o formulário Moodle efetivo e opções. Nenhum default oculto de senha/cidade/permissão.
- POST `/api/moodle/students/confirm` JSON `{previewId,expectedHash,confirmation:true}`: consumo único da prévia, resultados por aluno `{username,status:'created'|'updated'|'error'|'unknown',message}` e contagens. Timeout após envio deixa estado unknown e impede reenvio cego. Prévia obsoleta não envia.
- POST `/api/moodle/dates/preview` JSON `{courseId:number,input:DatePlanInput}`: ler formulários atuais e construir plano com `buildDatePlan`; retornar `{ok:true,previewId,hash,plan,targets}`. POST `/api/moodle/dates/confirm` JSON `{previewId,expectedHash,confirmation:true}`: reler estado, recusar deriva e aplicar exatamente o plano confirmado, preservando todos os outros campos. Retornar resultado por alvo e verificar datas efetivas após POST. Aplicação parcial é explícita; nunca prometer rollback/idempotência Moodle.

Todas as mutações dependem de Origin same-origin e sessão; corpo limitado, schemas estritos, cache no-store. Senhas, cookies, sesskey e credenciais ficam no servidor e não aparecem em arquivos, projetos ou logs. Cookie opaco httpOnly/sameSite/secure quando HTTPS; TTL e número de sessões/operações limitados. Nenhuma ação de envio em montagem/reabertura da UI. Session in-memory é suficiente para execução local, com expiração/relogin após reinício; não declarar serverless persistente.

HTTP Moodle deve ter timeout e resposta limitada, redirect somente para mesma origem, cookies nunca encaminhados fora dela. Ler formulários como dados, preservar pares ordenados e tipos select/checkbox/disabled; nunca executar HTML. Repositório upload vem da página/config, sem fallback numérico inventado. Erros retornam mensagens controladas, sem HTML/senha/CSV pessoal. Adapters têm testes de HTTP simulado, conflito/repetição/timeout e integração real separada na versão fixada do laboratório. Nenhum teste usa alunos reais.
